# Edit · the recipe

Alma reads this file whenever the user asks for a change to the cut ("swap the bottle take", "trim the head of S3", "add the music under S4", "captions on", "create subtitles"). The cut is one working cut, `cut/working.json`, kept by the harness. You change it with one drop file per piece of work: the harness checks it, takes it in as one step the user can undo, and saves it as a version with your note. The Edit page plays it. The code is `src/server/edit/` in the harness repo.

## The one rule

**You change the cut only with a drop.** Read `cut/working.json`, keep its `rev`, and write your change as one new file, `cut/alma/<YYYYMMDD-HHMMSS>.json`, with a one-line note. One drop per piece of work. The harness takes it in as one step in the history (the user can undo it) and saves it as the next version with your note. Never write `cut/working.json`, a version `cut/v<n>.json`, the history (`harness/cut-history.json`, `harness/cut-states/`) or an answer file, yours or anyone's, and never delete a file in `cut/`. Undo is the user's, on the Edit page. When the user asks where they can go back to: the History tab under the timeline lists every step and saved version, newest first, and the version menu in the header lists the saved versions; a press on a step moves the cut back or forward to it, and a press on a version opens it as one more step, which Undo takes back. The only things the harness itself writes beside the versions are `cut/renders/v<n>-proxy.mp4`, `v<n>-master.mp4`, `v<n>.log` and the files of renders with options (`v<n>-<kind>-<tag>…`, below); you write nothing in `cut/renders/` except a 480p or a master request (below).

**Every cut change goes through a drop first, the terminal way included.** A rough assembly joined with ffmpeg, a scene recut in `cut/*.nosync/`: write it as a drop *before* you render it, with the record's name in the note (`"rough assembly v10 from cut/rough-v10-list.txt"`). A `cut/*-v<k>-480p.mp4` or a review card of a cut newer than the newest version shows on the Edit page as "to confirm" (the record is ahead of the timeline) until a version catches up. See "From the record" below for how to turn the terminal's lists into a drop.

**What is not a cut change.** The renders of a version (its 480p, its master, the renders with options), the 1080p files and the final with its companions are made from a version. They need no version of their own and never count as "ahead". The film's finished picture and sound is the master the app renders from the cut (`cut/renders/v<n>-master.mp4`, below); older films also have a finished film in `cut/` or `social/` (`final`, `captioned`, `as-posted` in the name), which counts the same way.

## Steps

1. **Read `assets/films/<film>/cut/working.json`** right before you start, and keep its `rev`. It is the cut as it is now, the user's edits not yet saved as a version included: `version` names the newest version, and `edited: true` says the cut differs from it. Never start from a `cut/v<n>.json` instead.
2. **Make the change** on a copy of its `tracks` and `markers`.
3. **Write the drop**, `cut/alma/<YYYYMMDD-HHMMSS>.json` (the time now; add `-2` when that name is taken): `{"basedOnRev": <the rev you read>, "note": "<one line>", "tracks": [<all the tracks>], "markers": [<all the markers>]}`. The note says what changed and where, timecode in SMPTE: `"S7 head trimmed 12 frames at 00:01:56:01, ripple"`. Write the file to a temp name in the same folder, then rename it, so the harness never reads half a file. A name that ends in `.tmp` is never read:

   ```sh
   cd assets/films/<film>
   mkdir -p cut/alma
   stamp=$(date -u +%Y%m%d-%H%M%S)
   # write the JSON to cut/alma/$stamp.json.tmp (the Write tool, or python3 with json.dump), then:
   mv -n "cut/alma/$stamp.json.tmp" "cut/alma/$stamp.json"
   ```
4. **Read the answer**, `cut/alma/<the same name>.answer.json`, a few seconds later. `{"taken": true, "rev": 15, "version": "v241"}` means your change is in the cut as one step and saved as `v241` with your note. Tell the user in one line what changed. `{"taken": true, "same": true, …}` means your drop is the cut as it is: nothing changed, and no version was written. The harness checks a drop with the checks a render makes before it starts (the cut reads as a timeline, every clip's file is there and holds what its track needs, no clip reads past its file's end). It renders nothing: the Edit page plays the cut live.
5. **If it is refused**, the answer says `"taken": false` and `why` says why in plain words. Nothing was written to the cut. When the cut changed after you read it (the user, or another drop), `rev` is the cut's rev now and `since` lists the words of the steps made since: read `cut/working.json` again, make your change on it and write a new drop. When the cut does not check out, `problems` lists the reasons ("clip c12: out 9.2 s is past the end of …"): fix them and write a new drop. Never change or rewrite a drop or an answer; every try is a new drop with a new name.

**The 480p (to look at a change):** the harness renders it only when it is asked for. Write an empty file `cut/renders/v<n>.proxy-requested` when you need to look at your change, compare frames, or the stage notes ask for a check (QC of the cut reads it); the harness renders `cut/renders/v<n>-proxy.mp4` (480 on the short side, seconds for a three-minute film), records it in the version and writes its log, `cut/renders/v<n>.log`. A 480p that is there already is the answer (it is never made again); a refused version is not rendered (its log says why). The Edit page asks for it the same way, and the user can watch it from the Renders tab.

**To render the cut as it is now**, it must be a saved version. When you changed the cut, write the drop first: a taken drop names its version in the answer, and that is the version to render. When you changed nothing and `cut/working.json` says `edited: true`, the cut holds edits the user has not saved: ask the user to save (Save on the Edit page). Never save the user's edits for them.

**Master (1080p):** only when the user asks for it. Write an empty file `cut/renders/v<n>.master-requested`; the harness renders `cut/renders/v<n>-master.mp4` (1080×1920, CRF 18, from a `-1080p` sibling of each take when one exists, else the 480p take scaled) and records it in the version. A master takes a few minutes; say so.

**A master of a version can exist more than once.** A master made again is a new file beside the first, `cut/renders/v<n>-master-2.mp4`, then `-3`, each with its own record in the version (`renders.master` is the newest, `renders.earlierMasters` the ones before) and its own log (`v<n>-master-2.log`); the newest is the master of the version everywhere (the Edit page, the Finish page, the release), and the older ones stay on disk. A master is marked out of date, although the cut has not changed, when a shot now has a better full-size picture than it was made from: it has no record of its picture (made from the 480p scaled up), a take's `-1080p` or `-1080p-up` file or the upscaled cut is newer than it, or fewer shots would be scaled up now. Only then does "Render master again" on the Edit page (or writing the `.master-requested` marker again) make a new one; on an up-to-date master it does nothing.

**Renders with options** (asked from the Edit page; the request is `POST /api/films/<film>/cut/render` with `{version, kind, options}`, and the page sends it, not you). A render with options is a separate render of the same version; its files sit beside the plain one and never replace it, and the plain 480p and master are made exactly as without options. The options (`RenderOptions` in `src/server/types.ts`):

- `loudness: {lufs, truePeak}`: the full mix brought to an integrated loudness (LUFS, −40 to −5) with its true peak at or under `truePeak` (dBTP, −9 to 0; −1 when left out). The mix is measured first; when one gain gets there with the peak under the ceiling, that one gain is all that is done (`mode: "linear"`); otherwise the gain is followed by a true-peak limiter at the ceiling (`mode: "limiter"`). The written file is measured again (ebur128, true peak); the render's state keeps both measurements (`loudness.before`, `loudness.after`). If the written file's true peak is still over the ceiling, the render fails with that in words and writes nothing.
- `stems: true`: also the picture alone without sound (`.picture.mp4`), each sound track that plays alone (`.A2-Effects.wav`, named by the track's id and name), dialogue only (`.dialogue.wav`: the first audio track and the tracks named after it with a number, "Dialogue 2"), everything but dialogue (`.no-dialogue.wav`) and the mix (`.mix.wav`), 48 kHz 24-bit WAV, all as long as the film. The stems are at the cut's own levels, never through the loudness pass, and add up to `.mix.wav`.
- `leaveOut: {tracks, clips, cards}`: track ids and clip ids not drawn or heard in this render (black or silence in their place, the length unchanged); `cards: true` leaves out every clip whose label starts "Title card". For the picture for the upscaler without the cards: `{leaveOut: {cards: true}, stems: true}` and use its `.picture.mp4`.
- `small: true` (a master only, not with `stems`; refused in words on a 480p or with stems): the same film as a smaller file, for posting where about 100 MB is too much. It is the render with the same other options (the plain master, or for example the `lufs14-tp1` one) encoded again with x264 veryslow at CRF 21, the same pixel format and colour tags, the sound copied untouched. When that render is already on disk and not out of date it is used as it is and not rendered again; otherwise it is made first for this and not kept. The harness then checks the smaller file against it and records what it measured in the render's state and its `.json` (`small`: `from`, `fromBytes`, `bytes`, `frames`, `ssim`, `sound`): the same frame count, the sound byte for byte the same, smaller than it, and SSIM over the whole film at 0.98 or more; if any of these fails it writes nothing and says why ("the smaller file came out no smaller (98 MB against 96 MB): the normal one is the one to use"). It takes several times as long as the master. The user asks for it with "Smaller file" under the size in More renders; you do not ask for it yourself (there is no marker for it), you tell the user where it is.

The files are `cut/renders/v<n>-<kind>-<tag>.mp4` (the film with the loudness pass or the leave-outs; not written for stems alone), the stems as `v<n>-<kind>-<tag>.<stem>.wav` / `.picture.mp4`, and `v<n>-<kind>-<tag>.json`, written last, listing every file with what it holds and what was measured. The tag says the options: `without-cards-V3`, `lufs14-tp1`, `stems`, `small`, joined in that order (`v230-master-without-cards-stems.picture.mp4`, `v230-master-lufs14-tp1.mp4`, `v230-master-lufs14-tp1-small.mp4`, `v230-master-small.mp4`). The log of the version (`v<n>.log`) has each pass with its numbers.

**FCPXML export:** the Edit page's export button, or `curl -s "$HARNESS_URL/api/films/<film>/cut/export?version=v<n>&format=fcpxml" -o "$FILM/scratch.nosync/<name>.fcpxml"` (or where the user asks), gives FCPXML 1.10 of a version for another editor. Nothing of the film is made from it: the master is rendered by the app (above). Reading routes is fine; never POST to the cut routes yourself (the Edit page does that), except `cut/plan`, below.

## The shape (the contract is `Timeline` in `src/server/types.ts`)

This is a version file. `cut/working.json` has the same `fps`, `width`, `height`, `tracks` and `markers`, with `rev` in place of `version`. A drop holds `basedOnRev`, `note`, `tracks` and `markers` only.

```json
{
 "version": "v4", "basedOn": "v3", "by": "alma", "at": "2026-11-09T10:12:00.000Z",
 "note": "S3 shot 4: lamp take 3 in place of take 2 at 00:00:52:09",
 "fps": 24, "width": 1080, "height": 1920,
 "tracks": [
  {"id": "V1", "kind": "video", "name": "Picture", "clips": [
    {"id": "c24", "src": "assets/films/the-lighthouse/blocks/FIX-lamp-S3/takes/FIX-lamp-S3-seedance-take2-480p.mp4",
     "in": 0, "out": 4.041667, "at": 52.375, "label": "S3 · FIX-lamp-S3 · take 2",
     "takeRef": {"scene": "S3", "take": "FIX-lamp-S3 · take 2"}}]},
  {"id": "V2", "kind": "video", "name": "Inserts", "clips": []},
  {"id": "A1", "kind": "audio", "name": "Dialogue", "clips": [ {"id": "c24a", "…": "the same take's sound, same in/out/at"} ]},
  {"id": "A2", "kind": "audio", "name": "Effects", "clips": []},
  {"id": "A3", "kind": "audio", "name": "Music", "clips": []},
  {"id": "C1", "kind": "captions", "name": "Subtitles", "clips": [
    {"id": "sub1", "text": "Who opened\nthe door?", "in": 0, "out": 2.5, "at": 10},
    {"id": "sub2", "text": "It hums when it thinks.", "in": 0, "out": 3, "at": 31}]}
 ],
 "markers": [{"at": 156.375, "text": "To confirm: …", "by": "alma"}]
}
```

- `src` is relative to the film repo (`assets/films/<film>/…`), never an absolute path. `in`, `out` (seconds in the source) and `at` (seconds on the timeline) sit on frames: multiples of 1/fps, written to 6 decimals (`103/24` → `4.291667`).
- A clip lasts `(out − in) / speed` on the timeline (`speed` defaults to 1; `0.75` is slowed). `gain` is dB (default 0), `fadeIn` / `fadeOut` are seconds.
- `fadeIn` / `fadeOut` on a picture clip fade its picture from and to black (on an upper track, from and to the picture under it); on a sound clip they fade its sound. A picture clip and its `A1` twin are faded each by its own fields: a fade on one does not fade the other.
- `dissolve: <seconds>` on a clip mixes it with the clip that ends where it starts on the same track, over that many seconds centred on the join (half before the cut, half after): a dissolve on a picture track, a cross-fade (linear) on a sound track. The frames beyond each clip's cut point come from its file when the file has them, else its last or first frame is held (for sound, silence). Nothing moves: `at`, `in`, `out` and the film's length stay as they are, and clips still never overlap on a track. The picture and the sound are apart: a dissolve on a `V1` clip leaves its `A1` twin's sound cutting at the join; give the twin the same `dissolve` for the sound to cross-fade too. At most 10 s, and half of it must fit in each of the two clips (with the clip's other dissolve). A dissolve with no clip ending where it starts does nothing (the render log says so).
- `gainPoints: [{"t": 2, "db": 0}, {"t": 4, "db": -12}]` on a sound clip changes its level inside the clip: `t` is a second of the clip's source file (the clock of `in` and `out`, so a point stays on the same sound when the clip is split, trimmed, moved or sped up), the points in time order; the level runs straight in dB from one point to the next, stays at the first point's level before it and the last point's after it, adds to the clip's `gain`, and the clip's fades still apply on top. A point at timeline second T of a clip is `t = in + (T − at) × speed`. 1 to 500 points, `db` from −96 to 24. Only on sound clips.
- `flip: "h"` on a picture clip shows it mirrored left to right, on any video track, in the Edit page's player, the 480p and the master. Only on picture clips (a sound clip with `flip` is refused); the take's `A1` twin stays as it is. Leave the field out for the picture as shot.
- The user sets these on the Edit page too (13 Nov): a mirror, a fade on the picture alone, a dissolve or a sound cross-fade at a join, level points on an effect or the music. After any edit of theirs the page shortens a dissolve that no longer fits, to whole frames, or drops one whose join is gone, and says so in the version's note ("dissolve at S2 shot 3 shortened to 8 f", "… dropped: its join is gone"). Read the note before you put one back.
- The user's edits on the Edit page are steps in the history, kept at once, each with its words ("muted A2"); several presses of M or lock in a row are one step. They become a version only when the user saves. When the user undoes a change of yours, the page tells them it was yours and what it changed, in your note's own words: keep the note a plain account of the change.
- **Video clips are picture only.** A take's sound is its twin on `A1` (same `src`, `in`, `out`, `at`, `speed`; id with an `a` suffix). The lowest video track is the picture; a clip on `V2` and up covers it at its time.
- On one track the clips are in time order and never overlap (put an overlapping clip on another track). Gaps are black and silent.
- `muted` on a track hides or silences the whole track; on a clip it drops that clip. `solo` on an audio track plays only the solo tracks. A captions track draws its subtitle lines, and the cues of any `.srt` clip on it, in the film's caption style (PNG cards) when it is not muted. See "Subtitle lines" below.
- Clip ids stay as they are across versions; a new clip gets a new id (`c31`, `c31a`; music `m1`, effects `s2`).
- Labels with "(to confirm)" are facts the record could not settle (the migration put them there, with a marker). Keep the words until the user confirms; then take them out in a drop whose note says what the user confirmed.

## From the record (a concat list → one drop)

When the Edit page asks you to bring the timeline up to a cut the terminal workflow made ("rough assembly v10"), find what that cut was built from and write it as one drop for the whole catch-up (note: `"rough assembly v10 from <the list>"`). Never edit the list or the render.

- **An ffmpeg concat list** (`cut/rough-v<k>-list.txt`, `cut/<tag>-list.txt`, `cut/<scratch>.nosync/list.txt`): one `file '<path>'` line per clip, end to end. Each line becomes a V1 clip and its A1 twin: `src` = the path from `assets/films/<film>/…` on (drop everything before `assets/`; never an absolute path), `in` = 0, `out` = the file's length on a frame (`ffprobe -v error -select_streams v:0 -count_frames -show_entries stream=nb_read_frames -of csv=p=0 <file>` frames ÷ fps), `at` = the sum of the clips before it. A take gets `label` `"S<n> · take<k>"` and `takeRef`; a derived file (a scene cut, a name fix: `cut/namefix.nosync/S2-cut-v3.mp4`) gets a label from its name (`"S2 · cut v3"`) and no `takeRef`.
- **Neither exists** (a script joined the per-scene cuts without leaving a list): list the files it joined in the order of the render, write them as a concat list would be, and check the drop's length against the render (`ffprobe` frame count); say in the note what you could not confirm, and mark such clips `(to confirm)`.

When the drop is taken, ask for the 480p of the version its answer names (the marker above), compare it with the record's render (frame count; a look at the joins) and say in one line whether they match.

## What the timeline cannot say

A clip has a source, a stretch of it, a place, a speed, a level, fades and a mirror (`flip`). Anything else done to picture or sound (a crop or reframe, a colour pass, a cleaned or separated voice, a mix, a loudness pass) is a **new file made beside the original**, never over it, and the clip's `src` then points at the new file:

- Put the new file in the film folder where its stage note says, else in `cut/derived/`, named after its source and what was done (`S5-take3-cropped.mp4`).
- Change `src` on the clip (and on its `A1` twin when the sound changed too), keep `takeRef` so the Scene page still knows the take, and say what was done in the label and the note: `"S5 · take 3 · cropped"`, `"S5 take 3 cropped (cut/derived/S5-take3-cropped.mp4) at 00:01:20:00"`.
- A finished mix kept as a sound file (in `audio/master/`) is laid as one clip on its own audio track from 0, with the tracks it replaces muted, not removed. The film's finished sound is the cut's own sound tracks as the user leaves them (the dialogue, the music, the effects, their levels and fades): the master the app renders from the cut (`cut/renders/v<n>-master.mp4`) carries that mix, so the sound work goes on the cut's tracks and never into a separate finished file. The plain 480p and master make no loudness pass; a render with the `loudness` option does (above), and its file says so in its name.

## The timeline from day one (15 Nov 2026)

From the day the script is locked the film has a cut. Until its takes are in, the cut holds *planned* clips that the harness builds from the film's files: every line and action of the locked script on the Dialogue track at reading pace (`"plan": "line"`, with `who` and `text`), every planned shot of the shot lists on the picture track at its planned seconds (`"plan": "shot"`, with `text` and `inFrame`), and each shot's board, the first panel of the newest storyboard that has one (`"plan": "board"`, the panel as `src`). **You never write a planned clip**, in a drop or anywhere: the harness builds them, and keeps what the user changed by hand.

- **Bring the timeline up to date** after each of these pieces of work: the script locked, the shot lists written or changed, a scene's boards or a new previz take made (its lines then sit at the take's own times). One call: `curl -s -X POST "$HARNESS_URL/api/films/<film>/cut/plan" -H 'content-type: application/json' -d '{"action":"update"}'`. It is one step by you, saved as a version with words like "The shot lists: 34 planned shots" (the answer names the version), or `{"same": true}` when the cut already says what the files say. A scene whose take is in is left as it is. On a film with no cut the first call writes v1 from the script (the Edit page does the same when the user opens it). `GET` the same address says what an update would bring in (`pending`) without writing. `$HARNESS_URL` is this harness's address, set in your shell by the harness and named in your standing prompt; never put a port in its place.
- **A take in its boards' place**: the moment a scene's take lands, in the same step as the landing and before any check, without waiting for the user to name it. `land.py --kind take` does it itself as the take lands, by a drop into the cut (it waits up to `--drop-wait` seconds, 15 by default, for the answer; `--no-timeline` skips it for a test take). Exit 2 means the take landed but the drop was refused (its reason is printed): then make this call yourself, `-d '{"action":"take","scene":"S3","take":"take 1"}'` (the take's name or its file; without it, the scene's first take with a video). The scene's boards and lines leave and the take goes in their place, the whole take as one picture clip and its sound (the page shows it shot by shot); what follows moves by the difference in length. One step by you, saved as a version; the check runs after it, its findings go on the take's card, and a take that needs a redo stays in until its replacement lands. A later take never replaces the one in the film by itself: swapping it is a change of the cut like any other, a drop, when the user asks.
- **Put the boards back** is the reverse, the user's button under the Takes tab (`{"action":"boards","scene":"S3"}`): the take leaves the film and the scene's boards come back, one step that Undo takes back.
- A refusal is a 409 with `{"error": "…"}` in plain words (the script is not locked yet, the scene has no boards on the timeline, its take is in already). Add `"rev": <the rev of cut/working.json>` to have the call refused when the cut moved since you read it.
- **No render while anything is planned**: a version that still holds a line, a planned shot or a board is not rendered (the render answers 409, "It renders once every scene's take is in."). Do not write a render marker for one.

Which takes to make, when a go is needed and what a check must score are the stage notes'; this section is only how the timeline follows the work.

## A scene's layouts

A scene's layout is one previz take and the storyboard version rendered from it: its shots, their lengths and where its lines fall. The harness reads a scene's layouts from the files; you never write a list of them.

- **Which layouts a scene has**: `curl -s "$HARNESS_URL/api/films/<film>/layouts"` (add `?scene=S3` for one). Per scene, oldest first: `n` (the number the page shows, "Layout 2"), `key` (its previz take), `previz` (every previz take laid out the same), `storyboard`, `shots` (each with `n`, `id`, `t0`, `t1`, `name`, `line`: the words spoken in it, `framing`: the camera as a key, `board`), `takes` (`how`: `record` from the take's `<G>-take<N>-sent.json` `layout`, or `time` when it has none) and `current` (the layout the shown storyboard was made from). A layout is a previz take a video was made from, or the one the shown storyboard was made from. So every take must have its record of what was sent: `record_sent.py` writes the layout into it at submission.
- **Which layout the cut uses** is read from the cut: a clip with `"layout": <previz take>`, else the storyboard version of the scene's boards, else the previz take its lines are timed at, else the layout of its take.
- **Put a layout in the film** (the user's button "Use Layout 2 in the film" under the Takes tab; you only on the user's word): `curl -s -X POST "$HARNESS_URL/api/films/<film>/cut/plan" -H 'content-type: application/json' -d '{"action":"layout","scene":"S3","previz":2}'` (or `"layout": 2`, the number the page shows). Every picture and dialogue clip of the scene goes, and the layout's first take that landed goes in its place, whole, with its sound; a layout with no take yet puts its boards and its lines at its own times. Every clip it puts in carries `"layout": <previz take>`. What follows moves by the difference in length on every track, markers too. One step by you, saved as a version; `{"same": true}` when the cut uses that layout already; Undo takes it back. Add `"rev"` as for the other plan calls.
- **"Update the timeline" leaves a scene with `layout` clips as it is**, as it leaves a scene whose take is in.
- **A shot of another layout's take in a place of the layout in use** (from the Takes view, or a drop of yours on the user's word): its picture clip and its sound carry `"shot": <the place, 1, 2, 3 …>` and `"layout": <the previz take of the layout in use>`; the board and the planned lines under that place leave, the rest moves by the difference. Keep both fields on such a clip, and set them the same way in a drop that makes one.
- **A safe swap** is a shot whose `framing` and `line` are the same as the place's. Any other shot can still go into any place: the page marks it, lists what does not match (the line, the framing, the length) and puts it in. The step's note says it: `"S3 shot 2: take 1 in place of its boards (from Layout 1 into Layout 2: framed for another place)"`. When to say the warnings and what to propose is the stage note's: Flow v3.3 - 9 Edit, step 1.
- **Nothing here is ever overwritten**: an earlier layout keeps its previz take, its storyboard and its takes. Make a new layout's previz take and storyboard version as new files, as the stage note says.

## The film in shots (13 Nov 2026)

The Edit page shows the cut shot by shot. The harness finds the hard cuts inside every take that has a video file (its own takes, test takes and pick-ups alike) and keeps them in `harness/shots.json` in the film folder; you never write that file. What it means for the versions you read and write:

- **A version the user saved from the Edit page has one clip per shot.** A take that used to be one clip (`c9`, in 0, out 13.29) is then three (`c9`, `c9~2`, `c9~3`), each with its `A1` twin (`c9a`, `c9a~2`…), labelled `"S2 · short C · take 1 · shot 2"`. They play exactly as the one clip did. Keep them as they are; never join them back.
- **A drop you write may still use one clip for several shots** (`"… · shots 1 to 3"`). The page splits it for display and saves the split with the user's next change, with "· clips cut at their shots" at the end of that note.
- **A swap from the page** reads `"S2 shot 4: short B · take 1 in place of row picture · take 1, 29 f longer"`: the shot's clip and its twin replaced, everything after moved by the difference on every track, markers too.
- **A new take or pick-up needs nothing from you to show there**: once its video file is in its `takes/<take>/` folder under `generations/`, `blocks/` or `tests/`, it is cut into its shots and listed under its scene, ready to be tried in place. Name the scene in the path (`tests/<what>/S2/takes/take1/…`).
- **A delete or a trim made on the page with gaps closing moves every track and the markers**, as a ripple does here.
- **The options of an effect are the sound files in the folder of the clip's file.** The Edit page lists them when the user selects the effect, and the user steps through them and picks one; a pick changes only the clip's `src` and `label`. So every try of one effect goes in one folder (as in `audio/sfx/<effect>/`), a new try gets a new name there and never replaces a file, and the page shows it within 20 s without anything else to do. A `prompts.json` in the folder with `"prompts": [ … ]` gives each try its words on the page: entry n is shown for the file whose name has `try<n>`; add the new try's words at its number. A message that starts "Another option for the effect …" comes from that list.
- **A picture clip on `V2` or a track named "Over n"** was put there by the user dragging a shot over its neighbour on the page: it covers the picture under it for its length, and the clip under it is whole. Leave both where they are unless asked.
- **A track named after another with a number ("Effects 2", "Dialogue 2")** was made by the page for a sound that had to sit beside another at the same time (a paste, an unlinked sound). It is a track like any other.
- **Tracks can be gone, renamed or in another order** after the user's track menu on the page ("deleted track A4 Audio (3 clips)", "moved track A2 Effects up", "renamed track A4: Audio → Wind", "deleted 2 empty tracks: …"). Ids never change, so do not renumber or bring back a missing track; a missing `A3` is not a free number to reuse unless you are adding a track. Keep the order of `tracks` as you find it (picture tracks first). The order is only where the rows sit: which picture covers which still goes by the number in the id, `V2` over `V1`.
- **A scene of the film can have no clip in the cut, and a scene a missing shot number, on purpose**: the user took it out from the takes grid on the page ("S5 shot 4 taken out of the film (…)", "S5 taken out of the film (3 shots)"), the gap closed as for a ripple delete. It is not lost: do not put it back unless asked. "S5 shot 1 put back in the film (…)" is the user bringing one back from the grid.
- **`unlinked: true` on a clip** means the user set a picture clip and its sound free of each other on the page. Keep the field as it is. An unlinked sound often runs past its picture's cut and then sits on a track of its own beside the dialogue ("Dialogue 2", `A4` or the next free number): leave it there.
- **A clip's `speed` set from the page keeps its `in` and `out`**: the clip is shorter or longer on the timeline and what follows has moved. The render stretches its sound without changing the pitch.
- **"moved the join of A and B +12 f"** is the user moving a cut point on the page: A's `out` and B's `in` and `at` changed by the same amount (with their linked sound or picture), so A is longer and B shorter (or the other way); nothing else moved and the film kept its length.
- **A carried-over sound** ("S2 shot 3: its sound runs on 18 f after its picture (now on Dialogue 2)", "… starts 12 f before its picture …", "…, fading out") is the user letting one shot's sound be heard under the next shot or the one before (an Option-drag of one edge, or the menu's "Carry the sound over this join"). In the cut file: the sound clip has the same `src` as its picture and is in sync with it (`at` − `in` / `speed` the same), but its `out` (or `in` and `at`) reaches past the picture's end (or before its start); both carry `unlinked: true`; it sits on a track beside the dialogue ("Dialogue 2", the next free `A` number) and overlaps the neighbour's own sound, which is whole and as loud as before, often with a `fadeOut` (or `fadeIn`) as long as the stretch. It is deliberate: leave the sound, its track, its fade and the neighbour as they are, and when you change the picture keep the sound where it is. "…: its sound back to its picture's length, linked again" is the user undoing one.
- **Files the user put on the timeline by hand** (14 Nov). The Edit page lists the film's sounds (`audio/`, `voices/`, `cast/*/voice/`, `edits/`…), made pictures (`edits/`, `cut/cards/`, `cut/derived/`) and the files attached in the chat, and the user adds one at the playhead or drops it on a lane: a version `"added <name> on A3 Music at 00:00:12:00"` (a picture: `"added <name> on V2 Inserts at …, its sound on A2 Effects"`, the picture on a track above the main one, covering the picture under it, and its sound as a separate clip at the same place). Such a clip looks like any other: the whole file (`in` 0, `out` its length), labelled with the file's name, level 0 dB, no fades, an id like `pmweq29g30`. It is the user's choice: leave it, its place and its level as they are unless asked.
- **A file attached in the chat that the user placed was copied into the film** by the page: sound into `audio/added/`, video into `edits/added/`, under its own name without the time stamp (`rain-loop.wav`; `rain-loop-2.wav` when other bytes had the name). Those files are the user's; never move, rename or overwrite them, and when you lay one yourself use its path there.
- **"replaced <old> with <new> on A2 Music at …"** is the user swapping a sound clip's file for another from that list: only the clip's `src`, `label` and, when the new file is shorter, its `out` changed; its place, level and fades are as they were.
- **No clip reads past the end of its file** (`out` at most the file's length, 1.5 frames of rounding allowed; a clip's `speed` does not change what it reads). A version in which a clip reads further past its file's end than in the version it is based on is refused: its log names the clip, its `out`, the file's length and the frames over. A clip already like that in the version before still renders (its last frame held, its sound silent for the rest) and the page marks it in amber; when you touch that clip, bring its `out` back to the file's length.

## A variation of a take (14 Nov 2026)

On the Edit page's Takes view the user can right-click a shot (or a take's name) and pick "Edit this video…". You then get a chip named `Edit: S3 · Take 1 · shot 2` (or `Edit: S3 · Take 1` for the whole take). It carries the scene, the take's name, the take's file (`assets/films/<film>/…/takes/<take>/<file>.mp4`), the shot's number and its in and out in the take, in seconds; the user's message says what should change. How to make the new video is the film's own way of working, not this recipe's. What the page needs:

- **The folder.** When you start the variation, make the new take's folder beside the source take's, in the same `takes/` folder of that scene (for example `blocks/S3/takes/take1-variation1/`), and the video goes there when it lands, as any take's does.
- **`variation.json` in that folder, written as you start**: `{"from": "<the source take's file, exactly as the chip gave it>", "note": "<the user's words>", "startedAt": "<ISO time>"}`. From then on the Takes view lists it under the take it came from as "Take 1, variation 1", being made. When its video file is in the folder, the same row fills with its shots.
- **When it cannot be made**, add `"failed": "<why, in plain words>"` to that `variation.json`. The row then says so and offers nothing. Do not delete the folder.
- **A variation is never put in the film by you.** It replaces nothing: the user watches it in the Takes view and puts its shots in the film from there, or asks you to.

## Subtitle lines (14 Nov 2026)

Subtitles live in the cut as lines, one clip per line, on a track of kind `captions`. The Edit page shows them on the timeline and over the picture, the user moves, trims, splits, deletes and retypes them there, and every change is a step (Command-Z undoes it). The 480p and the master draw them as cards in the film's caption style (the Edit page's player draws them over the picture); a muted subtitles track, or one left out in More renders, gives a render without them.

- **A line** is `{"id": "sub1", "text": "Who opened\nthe door?", "in": 0, "out": 2.5, "at": 10}`: the `id` is `sub1`, `sub2`… and, like every clip's id, must not be used anywhere else in the cut (the effects clips are `s1`, `s2`…, so a line named `s1` is refused with "id used twice"); `text` is one or two rows with `\n` between them (never more, no row empty), `in` is 0, `out` is the line's length in seconds and `at` where it starts, both on whole frames like every clip. A line has no `src`, and none of a picture's or a sound's fields (`speed`, `gain`, `fadeIn`, `fadeOut`, `dissolve`). Ids: `s1`, `s2`… (keep the ids already there).
- **The track** is `{"id": "C1", "kind": "captions", "name": "Subtitles", "clips": [ … ]}`, the lines in time order. Two lines never overlap on one track. A track named "Captions" from before keeps its name.
- **The older form still works**: a clip whose `src` is an `.srt` file of the film (`{"id": "cap1", "src": "assets/films/<film>/subtitles/<name>.srt", "in": 0, "out": <the last cue's end>, "at": 0, "label": "<name>"}`) draws its cues from `in` to `out`. A captions clip has `text` or `src`, never both and never neither. On the page the user can split such a clip into lines ("Split into lines to edit": one line per cue, at the same times, one version).
- **"Create subtitles"**: the page's button (and "Create subtitles again…" in the subtitles track's menu) puts a request in your box naming the cut's version and listing the dialogue it knows (each dialogue clip's timecodes and take, and the script's lines of its scene where the film has them). It is yours to carry out: write the lines into the cut as one drop, as text lines on `C1 Subtitles` (add the track when there is none; when the request says the present lines are to be replaced, replace them), with a note such as `"subtitles: 42 lines on C1 from the dialogue of v230"`. How subtitles are worded, broken into lines, timed and styled: the stage notes say how.
- **The user's own changes** read as notes like `"retyped the subtitle at 00:00:12:04"`, `"moved “Who opened the door?” +6 f"`, `"split “It was never locked” at 1450 f"`, `"added <name>.srt on C1 Subtitles at 00:00:00:00"`, `"split <name> into 12 lines to edit on C1 Subtitles"`. Read them before you write lines again; keep the user's words unless asked.
- **Out of the cut**: the subtitles track's menu on the page has "Save as an .srt file", which downloads the lines as an `.srt` with the cut's times. Nothing is written in the film.

## Full-size pictures (13 Nov 2026)

The Edit page has a 1080p view: it plays each shot from the best full-size picture on disk and the tracks' sound over it. It finds them only by these names, so put every full-size file here:

- **A take redone in Seedance** at full size: beside its 480p file, `<take>-480p.mp4` → `<take>-1080p.mp4` (the same folder, the same name with `1080p`). Every shot of the cut that plays from that take then plays it, at its own in and out, and the master render uses it.
- **A whole take upscaled on Higgsfield** (the cheap pass, for a shot added or changed after the cut was upscaled): beside it, `<take>-1080p-up.mp4`, the whole take, so later trims stay covered. Read after the Seedance file.
- **A title card or other made piece** at full size: beside its small file, the same name with the cut's size, `<name>-480x854.mp4` → `<name>-1080x1920.mp4`. A picture file that is already at the cut's size is used as it is.
- **The upscaled cut**: `video/1080/cut-v<n>-1080.mp4`, frame for frame the same length and frames as cut `v<n>` (its 480p render upscaled, joined, nothing added or dropped; the 480p is made only when asked for, so write `cut/renders/v<n>.proxy-requested` first and wait for the file), without subtitles burnt in (the render draws the current cut's subtitles over it). The page maps every later version onto it by source, so trims, moves and deletions after `v<n>` stay full size. A frame of it is used only where the current cut draws the same thing there as `v<n>` did: where a fade, a dissolve, an insert or a mirror has changed since, that stretch comes from the shot's own file. Its working files stay under `video/1080/` (`segments/`, `upscale/`).
- Order per shot: the take's Seedance file, else its upscaled file, else a made piece's full-size file, else the upscaled cut, else the 480p (shown in amber as not upscaled).
- **The master render uses the same sources in the same order** as the 1080p view shows, the upscaled cut included: "Render master" (or a full-size render from More renders) builds each stretch from what the page plays there, and scales up from 480p only what the page shows in amber. The Renders tab and the render's log (`cut/renders/v<n>.log`, the line `picture:`) say what it was made from, for example `34 shots from the Higgsfield upscale of v230 · 2 from full-size originals`. To get a shot out of the amber, put its full-size file in place by the names above; nothing else needs changing.
- A request from the page ("Ask Alma for 1080p in Seedance 2.5", the first route: each take finalized at 1080p as its `…-1080p.mp4` beside its 480p; "Upscale on Higgsfield", the second) names the takes, their shots and timecodes and the cut's version; what it costs and what needs the user's word is the film's own rules (the stage notes), not the page's.
- **Takes marked for Seedance.** The user can mark takes on the page ("Redo in Seedance") without asking you for anything. The marks are kept in `<film>/harness/upscale-marks.json`, and while any take is marked every message from the page carries them in a chip, "Marked for Seedance · 2 takes". The file is `{ "note": "…", "seedance": [ { "src": "assets/films/<film>/…-480p.mp4", "take": "Short C · take 1", "scene": "S2", "markedAt": "<ISO time>", "cut": "v231", "shots": [ { "name": "S2 shot 1", "at": "00:00:12:06", "seconds": 4.7 } ] } ] }`: one entry a take, `src` as the cut's clips have it, `shots` the take's shots in that cut version with their timecodes. A mark is the user's note, not a go: nothing is spent on it until the user says so, and the quote and the go for a redo are yours as always. When the user asks you to mark or unmark takes, change this file (re-read it first, keep its shape, write the whole list; a temp file then a rename); the page shows the change. A take whose `-1080p.mp4` is on disk is done: the page drops its mark, and you may remove it from the file too.
- **What's next.** The Edit page's second tab, after Takes, is "What's next" (named "What is left" until 14 Nov): the whole film's next step, not a take's. Its label carries the number of steps still to do ("What's next 5"), and the panel says it in words ("5 steps left"). It lists seven steps, from the cut approved at 480p to the film posted on every platform, and where the app cannot know that a step is done (the cut approved when no answered yes card at the edit or finish stage names "cut v<n>", the sound listened through, a film without subtitles) the user ticks it, kept in `<film>/harness/left.json` as `{ "ticks": { "sound": { "at": "<ISO time>", "cut": "v239" } } }` with the cut version the tick was made on. Ask for the cut's approval on a yes card with the id `ASK-cut-v<n>`, `"at": "edit"` (or `"finish"`) and `cut v<n>` in its title, so this tab reads its answer as the cut approved. The ticks are the user's own word on what they have checked: read them, and never write, change or remove one. A master, the final or any render of an older version is judged by its cut's content, not by the version number (ASKS 49): when the cut it was made from renders the same as the cut now (a version can hold the same cut as an older one), the page says "the master of v235 · nothing changed since" and calls it done; when it differs, it says what in words ("out of date: 1 subtitle line moved since the master", "1 sound level changed since the final."), with the two version names quietly beside it. Compared is what the render reads (the picture size and frame rate, each track's id, kind, mute and solo, each clip's file, words, in, out, place, speed, levels, fades, dissolve, mute, mirror); names, notes, markers and ids are not. Say it to the user the same way, and do not offer to render a master again when the page says nothing changed.
- **What's next opens with what waits for the user**. Before the steps, the tab lists every card of "Waiting for you", in its order (your cards that ask, in the order the work goes, then the picks in the chains and at the gate), each question once: where your voice-round card asks about a character, the gate's Voices pick leaves that character out of this list ("Waiting for you" itself keeps both). Each row says the question, its quote for a go, and where it belongs; "Answer" opens the very card in place (answered the same way as on "Waiting for you"), "Open" goes to its page, and a card that asks to choose between sounds plays each one in its row. A step that such a card holds up says so in amber ("Waits for your yes on “S1 and S2: the storyboards v2”"): a card counts against its own step while that step is still to do, else against the step to look at. The tab's label counts both ("What's next 4 for you 8 left"), and your chip reads "What's next · 4 wait for you · 8 steps left · the first takes". So the list stays true only if "Waiting for you" does: close or answer a card the moment its question is settled (recipes/show.md).

## Reasons beside the History tab's steps

The user can write why they made a step: "Why?" beside a step of theirs in the History tab keeps a line for it. The harness keeps the reasons in the film's `harness/cut-reasons.json`, by the step's rev in `harness/cut-history.json`, with the step's own words and time copied in, so a reason still says what it is about after its step has left the history:

```json
{"format": 1, "reasons": [{"rev": 412, "step": "trimmed the head of S7 shot 2 by 72 frames", "stepAt": "2026-11-19T14:30:00Z", "by": "user", "reason": "the bottle moved too slowly at the start", "at": "2026-11-19T14:31:10Z"}]}
```

No message comes when a reason is written. Read the file before you change the cut and whenever the user's reasons are wanted; never write it.

## Conventions

- **One drop per piece of work**, with its note in one line, SMPTE timecode at the film's fps (`00:01:10:00`), decimal seconds only inside the JSON.
- **V1 and A1 of a block move together**: whatever you do to a take's picture you do to its sound twin, unless the user asks for a split edit (J or L cut), and then say so in the note.
- **Music sits at −12 dB** on its own track with 2 s fades in and out, unless the user says otherwise or the file is a bed already mixed as the sound note says (`audio/score/song-v<N>-as-mixed.wav`): that one is laid at 0 dB with no fades of its own, since its level, dips and fade are in the file. Effects go on `A2`.
- A ripple (removing or shortening something and closing the gap) moves every later clip on every track by the same amount, inserts, effects, music and markers included. Subtitle lines follow what the picture shows: a line wholly inside what was removed goes with it, one that straddles the cut is shortened to what is left, and an `.srt` clip over the cut is split at it (two clips of the same SRT: the first `in 0 → out <cut>`, the second `in <cut + removed> → out <end>` placed at `<cut>`) so the words stay on the lips. The Edit page does all of this by itself.
- Keep the pick-up naming in labels: `S3 · FIX-lamp-S3 · take 2`.

## Common operations

**Replace a take** (the user picked another take of the same shot): in the V1 clip and its A1 twin, change `src`, `label`, `takeRef`; keep `in`/`out` when the new take has the same timing, else set them to the stretch the user wants (same length keeps everything after it in place; a different length is a ripple, see above). Note: `"S3 shot 4: lamp take 3 in place of take 2 at 00:00:52:09"`.

**Trim a head** by k frames: on the clip and its twin, `in += k/fps`; for a ripple, every later clip on every track `at -= k/fps`; without a ripple, `at += k/fps` on the clip and its twin (a k-frame black gap opens before it). Trim a tail the same way with `out -= k/fps`.

**Ripple delete a shot**: remove the clip and its twin; every later clip on every track `at -= <its length>`. Note: `"ripple delete S6 shot 2 (00:01:39:03, 30 frames)"`.

**Add music at −12 dB with 2 s fades**: on the music track (`A3`; add `{"id": "A3", "kind": "audio", "name": "Music", "clips": []}` if missing), a clip `{"id": "m1", "src": "assets/films/<film>/audio/music/<file>.wav", "in": 0, "out": <seconds of it to use>, "at": <where it starts>, "gain": -12, "fadeIn": 2, "fadeOut": 2, "label": "<title>"}`. The file must be in the film folder first.

**Mute a track**: `"muted": true` on the track (the sound or picture stays in the file, it just does not play). Unmute by removing the field.

**Subtitles**: see "Subtitle lines" below.

**Add a title card**: the card is a clip like any other. Make it as a video file at the film's size and fps, with its own sound if it has one (how it looks is the stage notes' and the user's call), in the film folder (`cut/cards/<name>.mp4`, or `edits/<name>/` where the film already keeps one; both show on the Edit step under "Title cards and made pieces"). Insert it on `V1` at its place, its sound on `A2`, and move every later clip on every track by its length, captions and markers included. Label it `"Title card · <its words>"`, no `takeRef`. Note: `"title card (3 s) inserted before S1 at 00:00:00:00, ripple"`.

**Splice a word** (a re-voiced or cloned word laid over a take's own sound): picture stays as it is. Split the take's `A1` twin into three clips of the same `src` at the word's start and end (ids `c12a`, `c12a2`, `c12a3`; the split points on frames), then replace the middle one's `src`, `in` and `out` with the fix file's, same `at` and same length so the lips keep their place. The fix file is the one stage 3 makes for the edit (the word placed and matched as that note says, in `voices/names/…` or `voices/clone…/…`); this recipe only lays it. When stage 3 hands over a whole patched voice-only file for the take, replace the `src` of the whole A1 twin with it and split nothing. Label the middle clip `"S2 · word fix “island”"`. Note: `"S2: “island” re-voiced at 00:00:31:10 (voices/names/island-v3.wav)"`. The fix file must be in the film folder first; it then also shows on the Sound page.

**Back to v3**: the user does this on the Edit page (opening v3 there is one step they can undo). When the user asks you to, write a drop with v3's `tracks` and `markers` and the note `"back to v3"`.

**Ask for the 480p**: an empty `cut/renders/v<n>.proxy-requested`, when you need to look at a version.

**Ask for a master**: an empty `cut/renders/v<n>.master-requested`, only on the user's word.

**A smaller file of a master** (for posting): the user ticks "Smaller file" in More renders on the Edit page, with the full size and any loudness or leave-out; it lands as `cut/renders/v<n>-master-<tag>-small.mp4` (`v<n>-master-small.mp4` from the plain master). Say so when the user asks for a smaller file; you write no marker for it.
