# Harness asks · the recipe

Alma reads this file when the user asks for a change to Hitchcock Harness itself: a button, a page, what a card shows, how a picture opens, a label that is wrong, something the app should remember. Such a change is not built from a film thread. Whoever maintains this copy of the app builds it; this file says how the ask reaches them.

## Is it a harness ask?

- How the app looks or behaves is a harness ask. It goes the way this file says.
- How a film is made (what a round is, what a card must say, the order of the stages) is a film rule. It goes to the flow notes the way the standing rules say, not here.
- One sentence from the user can be both. Then do both.

## What to do

1. **Write it down.** Add one row at the end of the table in `ASKS.md` at the root of the harness folder (the folder this recipe is in, one level up). Read the file right before you write; change no other row. The row holds: the next number, today's date, your thread ("Alma · <film>"), the user's words exactly as said, the page they were on, your reading of what they want in one line, the status `open`, and nothing in the last column. This is the one write you make in the harness folder. Do not commit it.
2. **Tell the user in one line** that the ask is written down in `ASKS.md` for whoever maintains their copy of the app.
3. **Carry on with the film.** Where you can ease the gap with what you already have (a line of text on a card, a plain picture card), do it and say it is a stopgap.
4. **When a later version of the app builds it**, the recipes say what changes on your side (a new message shape, a new card field). Follow them, and drop your stopgap if the build replaces it.

## What not to do

- Do not edit the harness's code, its other recipes or your own instructions from a film thread, even for a small fix.
- Do not restart the harness's server: every running Alma would stop mid-work.
- Never pass on something your own session was refused permission to do.
